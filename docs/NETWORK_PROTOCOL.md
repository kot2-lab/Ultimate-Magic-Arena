# オンライン対戦 通信・サーバー設計案

状態: 準備中の設計案。未実装。サービス・認証・費用の確認とユーザーの決定後に確定する。
対象: 将来のオンライン招待対戦。現行Ver.1.4.4は引き続きローカル保存のCPU対戦版。

## 1. 目標

- 2人のプレイヤーが同じ対戦状態を見て、手番制の対戦を行う。
- クライアントは操作の意図だけを送る。HP、MP、ダメージ、乱数、勝敗、レーティングはサーバーが計算する。
- 通信切断後に同じ対戦へ復帰でき、重複操作や古い手番の再送で結果が二重適用されない。
- オフラインCPU戦と現在のブラウザーセーブを保ち、オンライン機能を後から独立して追加する。

## 2. 構成候補（まだ未決定）

Cloudflareを候補にする場合の責務分担:

- **Workers**: HTTPS API入口、認証情報の検証、入力のサイズ・形式検査、レート制限、HTTPエラー整形。
- **Durable Objects**: 対戦ルームごとの権威サーバー。WebSocket接続、手番状態、締切、再接続猶予、イベント順序を管理する。
- **D1**: アカウント参照、プロフィール、確定した試合結果、ランキングなど永続データの候補。
- **KV**: 読み取り頻度の高い公開設定のキャッシュ候補。対戦状態、残高、勝敗など正本データには使用しない。

Durable ObjectsはWebSocketによる接続維持と複数クライアント間の状態調整に向く。WebSocket Hibernationを使う場合は、休止・再起動後に必要な状態を永続化し、常時メモリーに残る前提を置かない。各ルームの正式状態・永続データの保存先は実装前に確定する。

この候補は採用決定ではない。アカウント方式、独自ドメイン、運用費、利用上限、バックアップ方法、データの所在と削除方法を比較してから決定する。

## 3. 権威ある対戦処理

1. サーバーが認証済み接続とプレイヤーの対戦参加資格を確認する。
2. クライアントは行動種別、魔法ID、対象レーン、現在の手番番号、重複防止IDを送る。
3. サーバーは参加者、現在の手番、制限時間、行動可能状態、魔法所持・MP・移動先を検証する。
4. サーバーだけが乱数を生成して戦闘ルールを実行し、新しい状態とイベント番号を記録する。
5. サーバーは両者へ同一の確定状態と表示用イベントを配信する。

クライアントからHP/MP、命中、クリティカル、状態異常、与ダメージ、勝敗、レーティングを受け取ってはならない。これらを含む状態変更要求は拒否する。

## 4. 接続と時間管理

- HTTPSでルーム作成・参加を行い、対戦中はWebSocketで双方向の手番イベントを送る。
- 接続時にOrigin、認証、参加権、ルーム状態を検査し、ルームIDだけを知っていても参加できないようにする。
- 手番の開始時刻・締切はサーバー時刻を正とする。現行CPU戦の15秒をそのまま採用するか、通信遅延を含む猶予を設けるかは対戦テスト後に決める。
- Durable Objectの手番締切は`setTimeout`/`setInterval`に依存せず、休止後も復元できるアラーム等の永続タイマーで管理する。
- 再接続猶予の間は対戦状態を維持し、再接続時に最新スナップショットとイベント番号を送る。猶予終了時の勝敗・無効試合規則は公開前に明示する。
- クライアントは自動再送時に同じ操作IDを使う。サーバーは既処理の操作IDを再適用せず、確定済み結果を返す。

## 5. 認証・アカウント・既存データ

- 認証プロバイダーは未決定。本人確認・アカウント回復・不正利用対策・費用を比較してから採用する。
- 認証用秘密鍵・API秘密情報を静的サイト、ビルド成果物、GitHub公開リポジトリへ置かない。
- 長期トークンを`localStorage`へ保存しない。Cookie方式または短命アクセストークン等を、選んだプロバイダーの安全な推奨方式に従い設計する。
- 新規アカウント導入時も既存のローカルセーブは自動送信・上書きしない。本人が選ぶエクスポート/移行、競合確認、復旧手段を先に用意する。
- 管理者機能はオンライン対戦の認証とは別のロールとし、将来の管理画面要件（多要素認証、短命セッション、試行制限、監査ログ、API単位の認可）を満たせるまで実装しない。

## 6. 開発前提と移行境界

- 現在の`src/battle.js`はCPU戦ロジックを持つが、乱数の既定値が`Math.random`。サーバー移植前に乱数供給を明示的に注入できる形を保ち、サーバーが乱数源を所有する。
- 戦闘ルールをサーバーとブラウザーで別々に再実装しない。共有可能な純粋ロジックに分離し、同じ入力から同じ遷移を検証できるテストを整備する。
- クライアントのアニメーションはサーバー確定イベントから再生し、演出時間がゲーム状態や締切を変更しない。
- オンライン試作は本番GitHub Pagesと本番データベースから分離し、テスト用アカウント・環境・保存領域を使う。
